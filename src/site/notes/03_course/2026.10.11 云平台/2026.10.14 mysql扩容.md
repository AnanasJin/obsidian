# mysql扩容
## 注意事项
1. mysql扩容必须双数扩容。
2. Mysql扩容需要在扩容后检查扩容服务器的u01和u02分区挂载的是否正确。
3. 仔细检查磁盘分区，如果是同机型扩容磁盘分区需要跟线上一致，如果是异构机型需要参考文档，文档中没有的，可以跟装机模版中的aliclone.json进行核查。
4. 每一步做完都要截图。

## 阿里云飞天基础运维平台 MySQL 扩容流程

> [!note] 适用范围与资料依据
> 结合本页注意事项和 [[03_course/2026.10.11 云平台/2026.10.12 扩容交付\|扩容交付培训笔记]]，这里按增加 MySQL 平台承载节点整理流程。单个数据库实例升配、扩存储空间需另查对应方案。以下包含通用运维检查建议；现有资料未提供 MySQL 专项操作手册或页面截图，具体菜单、服务角色、任务名称和执行顺序以对应版本正式方案为准，待核实。

### 1. 确认扩容对象和实施条件

- 核对环境标识、地域及可用区（如适用）、MySQL 产品、目标集群、SRG（机器组）和服务角色，记录现有节点及本次新增节点清单。
- 按本页培训要求，**本次新增节点数量为双数**；成对规则具体作用于哪个角色、机器组及故障域，需核对 MySQL 专项方案，不能仅凭总数为双数判断规划正确。
- 确认同构或异构扩容。同机型核对现网硬件和磁盘布局；异构先确认机型适配结论、是否允许混部及是否需要新增 SRG，不直接套用 ECS 的处理方式。
- 核对现网产品版本和基线，确认扩容工具支持本次 MySQL 场景。已有集群增加节点按匹配的扩容方案选版；如涉及升级，需在方案中单独明确。
- 按项目要求完成变更审批、账号授权、实施窗口、业务影响和异常处理安排；核查现有服务、告警及备份状态，记录扩容前基准。

### 2. 完成资源与朱雀规划

1. 核对商务配置单、环境信息和交付打标状态，确认本次产品、机型、数量与实际到货一致。
2. 选择匹配的产品基线；涉及多产品时按需组合自定义基线，逐项确认版本及依赖。按方案准备软件包，不把软件包与规划包混用。
3. 在朱雀中确认目标集群、SRG、服务角色及新增数量，区分继承的现网数量与本次新增数量。
4. 核对服务器 SN、机型、机位、主机名、产品用途、接入交换机和地址规划，避免将其他产品的服务器加入 MySQL 集群。
5. 补齐机柜、供电、布线、网络接口、地址池及必要网络配置；涉及网络扩容时先完成相应实施与验证。
6. 涉及 PaaS/IaaS 两侧规划时，核对同步后的设备、资源和地址映射；完成规划并下载本次规划包。MySQL 场景是否还需要其他 PaaS 侧文件，待核实。

### 3. 进入 ASO，完成扩容准备

1. 使用本环境确认的 ASO 地址和获批账号登录，核对环境与扩容支持范围。旧版环境是否使用 ASI，以版本方案为准。
2. 按方案进入扩容流程，加载所需规划包、软件包等材料，复核识别出的产品、集群、机器组、机型和节点清单。
3. 执行方案要求的前置检查，确认工具依赖、节点管理连通性、网络和资源条件满足要求。失败项查明原因后处理，不直接忽略。
4. 从飞天基础运维平台核对资源和集群信息。关联培训演示过从“资源管理”进入新版天机；**MySQL 专用扩容入口、具体菜单路径及其与 ASO 的衔接待核实**。

### 4. 按方案装机，检查磁盘分区与挂载

装机前先复核目标设备 SN 和 IP，确认操作对象均为本次新增节点。检查装机模板与机型匹配后，按方案执行装机，并在部署 MySQL 服务前检查磁盘；扩容完成后还要复查一次。

| 检查项 | 核对方法与要求 |
| --- | --- |
| 物理磁盘和系统识别结果 | 核对磁盘数量、类型、容量及 RAID/逻辑卷布局（如适用），与机型方案一致。 |
| 同机型分区 | 与线上同机型、同角色节点对照分区、文件系统、容量和挂载配置。设备名可能不同，需按实际设备、UUID 或逻辑卷关联核对。 |
| 异构机型分区 | 以适配文档为依据；文档缺项时核对对应装机模板中的 `aliclone.json`，参数仍不明确时找方案或适配人员确认。 |
| `/u01`、`/u02` 实际挂载 | 确认两者按方案挂载到预期设备，容量、文件系统及挂载选项正确；不能只看目录存在。具体用途及容量比例待核实。 |
| 持久化配置 | 核对 `/etc/fstab` 或平台规定的挂载机制与当前状态一致，避免系统启动后未按预期挂载。不为验证而擅自重启节点。 |
| 目录权限 | 按方案检查服务目录的属主、属组及权限，避免服务无法访问；不自行假定账号或递归修改权限。 |

以下为登录新增节点后的只读检查示例，不属于平台专用扩容命令：

```bash
lsblk -f
findmnt --mountpoint /u01
findmnt --mountpoint /u02
df -hT / /u01 /u02
cat /etc/fstab
```

`findmnt --mountpoint` 用于检查该目录本身是否为挂载点；`df` 用于辅助核对其所在文件系统和容量。目录存在、`df` 有输出，都不单独证明挂载正确。挂载方式以方案为准；未挂载或挂错盘时先处理并复核，避免服务把数据写入根分区。

### 5. 执行产品扩容

1. 装机、网络、分区和挂载检查通过后，按匹配方案继续 ASO 或平台中的 MySQL 产品扩容任务。
2. 提交前再次核对目标集群、SRG、服务角色、节点清单及新增双数要求；部署范围与已确认规划一致。
3. 按工具流程部署所需组件并将新增节点纳入目标产品，保留任务编号、各阶段结果及错误日志。具体服务角色、部署参数和操作按钮待核实。
4. 关注现有集群、数据库实例及承载业务状态；是否涉及数据迁移、实例调度或容量开放，按专项方案执行，不将“节点加入成功”等同于这些动作已经完成。

### 6. 扩容后检查与验收

- **平台资源**：新增节点数量、设备身份、集群/SRG/角色归属与规划一致，任务完成且节点状态符合方案要求。
- **主机与存储**：逐台复查 `/u01`、`/u02`，确认扩容后仍挂载正确；核对磁盘容量、权限、空间使用及磁盘 I/O 异常。
- **产品服务**：检查方案规定的 MySQL 相关组件、健康检查、监控和告警，确认无本次扩容引入的异常。
- **数据库实例**：核查受影响实例的连接及运行状态；涉及主备或复制时检查相应状态和延迟，涉及数据迁移时检查迁移结果。阈值与观察时长按方案执行。
- **容量与业务**：确认平台识别并可使用新增资源，与扩容前基准对比；按获批验证方式检查业务访问、关键查询和交易，不直接向生产业务表写入测试数据。

### 7. 异常处理与转维

- 任务失败时先记录失败阶段、节点、错误信息和任务编号，确认已完成的步骤及现网影响，再按方案恢复或重试，避免重复提交造成状态不一致。
- 分区、挂载或节点归属不正确时，暂停后续部署，先核清原因。装机、格式化、调整分区等不能作为通用重试手段。
- 新节点已承载实例或数据后，退出节点、回退或重新装机需按产品方案处理，不能直接删除节点。
- 验收后更新节点台账、实际规划、版本、容量、监控和实施记录，移交验证结果及遗留问题。
